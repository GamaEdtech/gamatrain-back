# Migrations

## Inventory

- **116 migrations** in `src/Infrastructure/Infrastructure/Migrations/` (one `<Timestamp>_<Name>.cs` + one matching `<Timestamp>_<Name>.Designer.cs` per migration, plus one shared `ApplicationDBContextModelSnapshot.cs`).
- Most recent: `20260803084223_MoveBillingIntervalToSubscriptionPlanPrice` — moves `BillingInterval` off `SubscriptionPlan` onto `SubscriptionPlanPrice` (and adds a snapshot copy on `UserSubscription`), backfilling both from the old column before dropping it (see `docs/business/subscriptions.md`).
- Span: `20250130092339_Init` (2025-01-30) → `20260803084223_MoveBillingIntervalToSubscriptionPlanPrice` (2026-08-03).
- **DbContext:** `GamaEdtech.Infrastructure.EntityFramework.Context.ApplicationDBContext` (`src/Infrastructure/Infrastructure/EntityFramework/Context/ApplicationDBContext.cs`) — the only context in the solution, so there's never any `--context` ambiguity to resolve.

## Naming convention

Migration names are timestamp-prefixed (`yyyyMMddHHmmss_Name`), auto-generated by `dotnet ef migrations add <Name>`. In practice `<Name>` is usually PascalCase and describes the change (`SchoolFields`, `TransactionIdIndex`, `GenderType`, `SchoolRank`), but this is **not strictly enforced** — a handful of migrations were added with free-text, space-containing, lowercase-first names, e.g.:

- `20250720173644_add SchoolId to user.cs`
- `20250726201406_set schoolId & cityId nullable.cs`
- `20250810155344_add ReferralId To ApplicationUsers Table.cs`
- `20250912071909_Edit Gender Column in ApplicationUser.cs`

These still work (EF only cares about the timestamp prefix for ordering), but new migrations should follow the tighter PascalCase style (`AddSchoolIdToUser`, not `add SchoolId to user`) for consistency with the majority of the history.

## No squashing/baselining

The project does **not** squash or baseline old migrations — every migration since `Init` (`20250130092339_Init.cs`) is still present and gets replayed in order on a fresh database. `ANALYZE.md` (§7.5) flags this as a build/analyzer-speed cost worth addressing (EF supports resetting to a single baseline migration for new environments while keeping full history in git), but as of this writing no such squash has happened — treat every migration in the folder as load-bearing for anyone provisioning a database from scratch.

## Adding a new migration

From the `src/` directory (the solution root, `src/GamaEdtech.sln`):

```bash
dotnet ef migrations add <Name> \
  --project Infrastructure/Infrastructure/GamaEdtech.Infrastructure.csproj \
  --startup-project Presentation/Api/GamaEdtech.Presentation.Api.csproj

dotnet ef database update \
  --project Infrastructure/Infrastructure/GamaEdtech.Infrastructure.csproj \
  --startup-project Presentation/Api/GamaEdtech.Presentation.Api.csproj
```

Notes:

- **`--project`** must point at the Infrastructure project (that's where `Migrations/` lives and where the new files get written); **`--startup-project`** must point at the API project, because there is no `IDesignTimeDbContextFactory` in the repo — `dotnet-ef` builds and boots the API's own host/DI at design time to resolve `ApplicationDBContext` and its configuration (connection string, etc.). The startup project must therefore compile cleanly and its configuration (`appsettings.json` / `appsettings.Development.json`) must point at a reachable SQL Server instance, or `migrations add`/`database update` will fail while trying to construct the context.
- Only one DbContext exists (`ApplicationDBContext`), so no `--context` flag is needed.
- **Migrations also apply automatically at process startup** — `Host.RunInternalAsync` calls `context.Database.MigrateAsync()` before the web host starts listening whenever the generic `Startup<TUser, TRole>` is used (`src/Core/Common/Hosting/Host.cs:63-83`). This means in normal local dev you often don't need to run `dotnet ef database update` by hand at all: just `dotnet run --project Presentation/Api --launch-profile GamaEdtech` against a behind-schema database. Manual `database update` is mainly useful for inspecting/generating SQL ahead of time (`dotnet ef migrations script`) or applying migrations without booting the full app.
- CI does **not** run migrations as a deploy step — the migration-related lines in `.github/workflows/main_gamaedtechv2.yml` (`dotnet ef database update`, `migrations bundle`) are present but commented out. In deployed environments, migrations are presumably applied by the auto-migrate-on-startup behavior above; there is no documented separate migration-bundle deploy step currently in use.

## Notable migrations

### `ImportLocations` — the one bulk-data-seeding example

`20250203080130_ImportLocations.cs` (`src/Infrastructure/Infrastructure/Migrations/20250203080130_ImportLocations.cs`) is the only migration in the project that bulk-seeds data via an embedded resource rather than `migrationBuilder.HasData(...)` or a handful of inline `InsertData` calls:

1. A `.resx` resource (`src/Infrastructure/Infrastructure/Resource1.resx`, generated accessor `Resource1.Designer.cs`) embeds a large text blob under the key `"Locations"` — a raw SQL script of roughly **156,000 single-line `INSERT` statements** into `Locations`, wrapped in `SET IDENTITY_INSERT ... ON` / `OFF`.
2. The migration reads the resource as bytes, decodes it as UTF-8, and originally executed the entire script as one `migrationBuilder.Sql(...)` call.
3. **The bug (now fixed):** submitting ~156k statements as a single batch exhausts SQL Server's query-compile memory on memory-constrained instances — **SQL error 701** ("There is insufficient system memory in resource pool 'default' to run this query"). This is a real operational risk for anyone running SQL Server with a small buffer pool (e.g. a dev container, a small VM, or the user-mode/proot SQL Server used for local dev in this environment).
4. **The fix:** the script is split on newlines and re-batched into **1000-line chunks**, each issued as its own `migrationBuilder.Sql(...)` call (`ImportLocations.cs:27-32`):

   ```csharp
   const int batchSize = 1000;
   var lines = sql.Split(["\r\n", "\n"], StringSplitOptions.RemoveEmptyEntries | StringSplitOptions.TrimEntries);
   for (var i = 0; i < lines.Length; i += batchSize)
   {
       migrationBuilder.Sql(string.Join(Environment.NewLine, lines[i..Math.Min(i + batchSize, lines.Length)]));
   }
   ```

   All chunks run over the same migration connection/transaction, so the `SET IDENTITY_INSERT Locations ON` at the top of the script and the corresponding `OFF` at the end still bracket every chunk correctly — chunking only changes how many statements SQL Server compiles per network round-trip, not the transactional/identity-insert semantics.

**Takeaway for future bulk-seed migrations:** if you ever need to embed a large generated SQL script in a migration again (large lookup-table imports, data backfills, etc.), follow this same pattern — chunk into batches of roughly 1000 lines/statements via repeated `migrationBuilder.Sql(...)` calls — rather than emitting the whole script as a single `Sql(...)` call, which does not scale past a few thousand statements on constrained SQL Server instances.

### `SchoolRank` — ranking system

`20260518191839_SchoolRank.cs` adds three plain nullable `int` columns to `Schools`: `CountryRank`, `StateRank`, `CityRank`. The migration itself is a trivial `AddColumn`/`DropColumn` pair — the actual ranking logic lives entirely in application code, not in the migration:

- `SchoolService.UpdateSchoolScoreAsync()` (`src/Application/Service/SchoolService.cs:1898-1975`) runs a single raw-SQL `UPDATE ... FROM` statement (via `uow.ExecuteSqlCommandAsync`) that:
  1. Computes a `RankScore` per school from comment ratings, presence of coordinates/website/email/phone/address, and image count (CTEs `CommentAgg`, `ImageAgg`, `RankScoreCalc`).
  2. Computes `CountryRank`/`StateRank`/`CityRank` as `DENSE_RANK() OVER (PARTITION BY ... ORDER BY RankScore DESC)`, partitioned by country, then country+state, then country+state+city (CTE `RankCalc`).
  3. Writes `RankScore`/`CountryRank`/`StateRank`/`CityRank` back onto `Schools` only for rows where a value actually changed.

  The column was originally named plain `Score`; renamed to `RankScore` on 2026-07-10
  (`20260710090320_RenameScoreToRankScore.cs`, a hand-written `RenameColumn`/`RenameIndex` pair —
  same shape as `20250913191122_Change Section To Board.cs`) once a separate, differently-purposed
  `Rating` field existed and the shared "Score" word became ambiguous between the two. See
  `docs/business/school-scoring-analysis.md` for the full history.
- This runs on a **weekly Hangfire recurring job** (`RecurringJob.AddOrUpdate<ISchoolService>("UpdateSchoolScore", t => t.UpdateSchoolScoreAsync(), Cron.Weekly(DayOfWeek.Sunday, 2, 0))`, registered in `src/Presentation/Api/Startup.cs:226`), i.e. ranks are a weekly batch recomputation, not maintained live on every write to `SchoolComments`/`SchoolImages`.
- Similar "add columns, then a Hangfire job maintains them" pattern applies to the denormalized `LikeCount`/`DislikeCount` counters on `Post`/`PostComment`/`SchoolComment`, kept in sync by `UpdatePostReactionsAsync`, `UpdatePostCommentReactionsAsync`, and `UpdateSchoolCommentReactionsAsync` (also registered in `Startup.cs:227-234`) — worth knowing when debugging "stale count" reports, since these are eventually-consistent, not transactional side effects of `Reaction` inserts.
