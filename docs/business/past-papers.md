# Past papers

Past papers (exam papers with their question, answer and extra files) are still served by gama-api: every past paper
endpoint and the MCP tools go through the proxy (`ICoreProvider`). They are being moved here one step at a time, and
each step is added without changing what users see. This document follows that move.

## Steps

| Step | What | State |
|---|---|---|
| 1 | Copy the paper files into the private bucket's `PastPaper` container, keeping gama-api's paths | done (127,653 files, verified) |
| 2 | Tables `PastPapers` and `PastPaperFiles`, and a job that copies gama-api's paper rows into them | done (production) |
| 3 | Copy what users bought on gama-api, so nobody pays for a file twice | done (production) |
| 4 | Copy the price data (gama-api's base price list) and reproduce its price rule exactly | done (production) |
| 5 | Check the copy: every row's file is in the private bucket, and record its size | this change |
| 6 | Switch the past paper endpoints from the proxy to these tables, in their own change | to do |

Until step 6, **nothing reads these tables**. Changing them cannot affect users.

## Ids never change

A paper keeps its gama-api id: `PastPapers.Id` is gama-api's `tests.id`, set by the copy, never generated by the
database. Paper URLs (`/paper/{id}`), search engine listings, purchases and download records all use that id, so a
changed id would break links and lose search ranking. When papers are created here (step 6), new ids must start above
the highest copied id, so they can never collide with a gama-api id.

## What is copied

`IPastPaperImportService.ImportAsync` (Hangfire job `ImportPastPapers`, run by hand from the dashboard, never on a
schedule) reads gama-api's database read-only (`ILegacyDatabaseReader`, `Migration:LegacyDatabase:ConnectionString`):

- `tests` → `PastPapers`. Every business field, under a clear name (`section` → `CoreBoardId`, `base` → `CoreGradeId`,
  `lesson` → `CoreSubjectId`, `test_type` → `CorePaperTypeId`, `msg` → `ReviewNote`, `bit_delete` → `IsDeleted`, ...).
  gama-api's processing flags (file move, thumbnail and search sync markers) are not copied. `Status` keeps gama-api's
  codes (`PastPaperStatus`: 0 pending, 1 confirmed, 2 rejected, 3 needs changes, 4 deactivated, 5 deleted, 6 edited).
- The paper's `q_file`, `a_file` and `q_file_word` → one `PastPaperFiles` row each (`Kind` Question, Answer,
  QuestionWord). The values `''`, `'0'` and `'fileMissed'` mean "no file" and are skipped.
- `tests_extra_files` → `PastPaperFiles` rows of `Kind` Extra, keyed by `CoreExtraFileId`; `CoreTypeId` says what the
  file is (a gama-api lookup item: insert, audio, ...). An extra file whose paper does not exist is skipped and counted.

`PastPaperFiles.Path` is gama-api's path inside its paper folder, unchanged (`2025/06/22/name.pdf`, or `name.pdf` for
older files), which is also the file's key in the private bucket's `PastPaper` container. Rows and files therefore match
without renaming.

The `Core...` columns hold gama-api ids (owner, teacher, board, grade, subject, topics, school, area) with no foreign
key yet: this backend's `Boards`/`Grades`/`Subjects` use other ids. The owner is linked to the local user with that
`CoreId` (`OwnerUserId`), at copy time or on a later run once the user is linked.

**The owner shown on a paper** is `DisplayOwnerUserId`: `OwnerUserId`, or, when the owner has no account here, the
fallback user `Migration:PastPapers:FallbackOwnerUserId` (production and sandbox: 56). It is display only: ownership and
commissions always use `OwnerUserId`, so the fallback user never earns from papers that are not theirs. Reads use only
these two columns (our user ids), never `CoreId`, so they keep working once `CoreId` and the `Core...` columns are dropped
at the end of the move. A fallback id that does not exist is ignored (those papers show no owner).

## Running it again

The copy can run any number of times: papers are added or updated by id, never duplicated, and never deleted. A paper's
own files follow gama-api (a cleared answer file is removed, a new one is added); an extra file removed in gama-api is
removed here. gama-api's MySQL runs in UTC; `Migration:LegacyDatabase:TimeZone` overrides that if it ever changes.
Run it once more just before the switch, so the copy holds the latest papers.

A test server sets `Migration:LegacyDatabase:MaxPastPapers` (the sandbox: 1000) and gets only that many papers by id,
with their files; extra files of the papers left out are skipped. `PastPapersFromId` starts the copy at a paper id, so the
sandbox can hold the newest papers (the ones people see on the live site) rather than the oldest. The copy never deletes,
so moving a test server's window means removing its old copied papers there first. Production leaves both unset and
copies everything.

## Prices

A paper must cost the same after the move, so gama-api's price rule is reproduced exactly in `PastPaperPricing` (pure,
tested against prices gama-api shows; nothing calls it until downloads move here):

```
main file:  round10(base(ext) * sqrt(pages) * factor(referee score) / 10 * the paper's PriceMultiplier)
extra file: round10(base(ext) * sqrt(length) * factor(referee score) / 10 * its type's price_multiplier)
```

- **Base price per file type** comes from gama-api's `files_price` table (admins edit it there), mirrored with its ids
  into `PastPaperFilePrices` by every `ImportPastPapers` run (added, updated and removed, so the copy always matches).
  Today: pdf 50, doc/docx 100, mp3 30. **A file type with no base price is free** (zip, wav, mp4...).
- **Referee factor** (`RefereeScore`): D (1) 0, C (2) 1, B (3) 1.5, A and A+ (4, 5) 2, none 0. A Word file whose factor
  is 0 gets 0.5 instead.
- **Extra files** use their type's own `price_multiplier` (the lookup item's metadata, copied with the types; 1 when it
  has none) instead of the paper's, and their `Length` instead of pages.
- **Rounding** is PHP's `round(x, -1)`: to the nearest ten, halves away from zero.

## Checking the copy

`IPastPaperFileCheckService.CheckAsync` (Hangfire job `CheckPastPaperFiles`, by hand, never scheduled) lists the private
bucket's `PastPaper` container in full first (a listing that fails part way changes nothing), then looks up every
`PastPaperFiles` row by its `Path`:

- **Found:** its `Size` (bytes) is stored; the paper page shows it.
- **Missing:** `Size` stays null with `CheckDate` set. The file copy missed it or gama-api never had it; the result lists
  up to 20 examples to look into.
- **Unused:** files in the bucket no row points to (left over from deleted papers or replaced uploads) are counted, not
  deleted.

Run it after the file copy finishes, and again after every rerun of the copy. It reads the bucket through
`IFileService.ListFilesAsync` (the configured provider; S3/R2 lists with `ListObjectsV2`).

## Purchases made on gama-api

Today the "already paid" answer for a paper file comes only from gama-api: this backend charges, then calls gama-api's
download, which records the purchase in its `payments` table (see `docs/business/content-delivery.md`). That history
must move with the papers, or every buyer would be charged again after the switch.

`IPastPaperPurchaseImportService.ImportAsync` (Hangfire job `ImportPastPaperPurchases`, by hand, never scheduled)
reads gama-api's `payments` through a column list, so card numbers, IPs and bank fields are never read. It keeps the
paid past paper files only: payment `type` 1 (question PDF), 2 (answer), 8 (question Word) and 12 (extra file, whose
`usage_id` is the extra file's id), with `status` 1, 2 or 3, the same rule as gama-api's own check. Each becomes:

- a `LegacyPastPaperPurchases` row, keyed by gama-api's payment id (a rerun updates it), and
- as soon as its paper is copied and its buyer has an account here (`CoreId`), a `ContentPurchases` row:
  `ContentType = PastPaper`, `ContentId` = the paper id, `Variant` = `Question` / `Answer` / `QuestionWord` /
  `Extra:{extra file id}`, `PaidBy = GamaApi`, `Points = 0` (gama-api took the money). The same file bought twice on
  gama-api is owned once: both copies point at one ownership row.

Ownership is only ever `ContentPurchases`; `LegacyPastPaperPurchases` is gama-api's history and the waiting room for
buyers who have no account here yet (most of them: an account is linked when its owner first signs in through the
gama-api bridge). The daily `LinkPastPaperPurchases` job (`LinkAsync`, reads only this database) moves those over once
the buyer or the paper is here. Run `ImportPastPaperPurchases` again just before the switch: purchases keep being
recorded on gama-api until then.

### Removing the purchase copy

`LegacyPastPaperPurchases` and its service are temporary, for the move only. Once gama-api is shut down and the last
`ImportPastPaperPurchases` has run, decide what happens to the purchases still waiting for a buyer (keep linking them for
a while, or let them go), then remove in one change:

1. the `ImportPastPaperPurchases` and `LinkPastPaperPurchases` jobs (`Startup.cs`), and delete them from Hangfire;
2. `IPastPaperPurchaseImportService`, `PastPaperPurchaseImportService`, `PastPaperPurchaseImportResultDto` and
   `PastPaperPurchaseImportTests`;
3. the `LegacyPastPaperPurchase` entity, with a migration that drops `LegacyPastPaperPurchases`;
4. this section and the matching lines in `docs/database/`, `docs/architecture/cross-cutting-concerns.md` and `CLAUDE.md`.

The ownership rows it made stay: they are ordinary `ContentPurchases` rows (`PaidBy = GamaApi`) and need nothing from the
copy. Nothing else reads the table, so removing it changes no behaviour.
