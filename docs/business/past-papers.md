# Past papers

Past papers (exam papers with their question, answer and extra files) are still served by gama-api: every past paper
endpoint and the MCP tools go through the switch (`IMigrationRouter`), whose route is `Legacy` until a server's settings
move it. They are being moved here one step at a time, and
each step is added without changing what users see. This document follows that move.

## Steps

| Step | What | State |
|---|---|---|
| 1 | Copy the paper files into the private bucket's `PastPaper` container, keeping gama-api's paths | done (127,653 files, verified) |
| 2 | Tables `PastPapers` and `PastPaperFiles`, and a job that copies gama-api's paper rows into them | done (production) |
| 3 | Copy what users bought on gama-api, so nobody pays for a file twice | done (production) |
| 4 | Copy the price data (gama-api's base price list) and reproduce its price rule exactly | done (production) |
| 5 | Check the copy: every row's file is in the private bucket, and record its size; copy the pictures | done |
| 6 | The paper page, paper lists and the exam page's paper link read these tables (`NativePastPaperSource`) when the route says so | built; `Legacy` until switched (sandbox first, through `Shadow`) |
| 7 | Downloads: price, charge once, the paid-file record here, signed private links (`PastPaperDownloadService`) | built; `Legacy` until `Migration:WriteRoutes:PastPapers.Downloads` is `Native` |
| 8 | A teacher's own papers: their list and a paper for the edit form | built; `Legacy` until `Migration:Routes:PastPapers.Teacher` is switched |
| 9 | A teacher's uploads, add, edit and delete | built; `Legacy` until `Migration:WriteRoutes:PastPapers.Teacher` is `Native` |
| 10 | Admin: every paper, review (status and notes), score, adding for a teacher | built; changes wait for `Migration:WriteRoutes:PastPapers.Teacher` = `Native` |
| 11 | The MCP reads | to do |

Only the native sources read these tables, and only when their route says so: `Migration:Routes:PastPapers.Website`
(`Shadow` or `Native`) for the pages and lists, `Migration:WriteRoutes:PastPapers.Downloads` (`Native`) for downloads,
`Migration:Routes:PastPapers.Teacher` for a teacher's own papers.
With no setting (production today) changing them cannot affect users.

## Ids never change

A paper keeps its gama-api id: `PastPapers.Id` is gama-api's `tests.id`, set by the copy, never generated by the
database. Paper URLs (`/paper/{id}`), search engine listings, purchases and download records all use that id, so a
changed id would break links and lose search ranking. When papers are created here (step 6), new ids must start above
the highest copied id, so they can never collide with a gama-api id.

## What is copied

`IPastPaperImportService.ImportAsync` (Hangfire job `ImportPastPapers`, run by hand from the dashboard, never on a
schedule) reads gama-api's database read-only (`ILegacyDatabaseReader`, `Migration:LegacyDatabase:ConnectionString`):

- `tests` → `PastPapers`. Every business field, under a clear name (`section` → `CoreBoardId`, `base` → `CoreGradeId`,
  `lesson` → `CoreSubjectId`, `test_type` → `CorePaperTypeId`, `msg` → `ReviewNote`, `bit_delete` → `IsDeleted`, ...).
  gama-api's processing flags (file move, thumbnail and search sync markers) are not copied. `Status` keeps gama-api's
  codes (`PastPaperStatus`: 0 pending, 1 confirmed, 2 rejected, 3 needs changes, 4 deactivated, 5 deleted, 6 edited).
- The paper's `q_file`, `a_file` and `q_file_word` → one `PastPaperFiles` row each (`Kind` Question, Answer,
  QuestionWord). The values `''`, `'0'` and `'fileMissed'` mean "no file" and are skipped.
- `tests_extra_files` → `PastPaperFiles` rows of `Kind` Extra, keyed by `CoreExtraFileId`; `CoreTypeId` says what the
  file is (a gama-api lookup item: insert, audio, ...). An extra file whose paper does not exist is skipped and counted.

`PastPaperFiles.Path` is gama-api's path inside its paper folder, unchanged (`2025/06/22/name.pdf`, or `name.pdf` for
older files), which is also the file's key in the private bucket's `PastPaper` container. Rows and files therefore match
without renaming.

The `Core...` columns hold gama-api ids (owner, teacher, board, grade, subject, topics, school, area) with no foreign
key yet: this backend's `Boards`/`Grades`/`Subjects` use other ids. The owner is linked to the local user with that
`CoreId` (`OwnerUserId`), at copy time or on a later run once the user is linked.

**The owner shown on a paper** is `DisplayOwnerUserId`: `OwnerUserId`, or, when the owner has no account here, the
fallback user `Migration:PastPapers:FallbackOwnerUserId` (production and sandbox: 56). It is display only: ownership and
commissions always use `OwnerUserId`, so the fallback user never earns from papers that are not theirs. Reads use only
these two columns (our user ids), never `CoreId`, so they keep working once `CoreId` and the `Core...` columns are dropped
at the end of the move. A fallback id that does not exist is ignored (those papers show no owner).

## Running it again

**gama-api's flags are `tinyint(1)`** (`is_paper`, `bit_delete`, `free_aggrement`). The reader reads them as numbers
(`TreatTinyAsBoolean = false`). Until 2026-11-16 they arrived as booleans and every copy read them as 0: every paper was
"not a paper", none was deleted. Run `ImportPastPapers` and `SyncLegacyTaxonomy` again after that fix is deployed.

The copy can run any number of times: papers are added or updated by id, never duplicated, and never deleted. A paper's
own files follow gama-api (a cleared answer file is removed, a new one is added); an extra file removed in gama-api is
removed here. gama-api's MySQL runs in UTC; `Migration:LegacyDatabase:TimeZone` overrides that if it ever changes.
Run it once more just before the switch, so the copy holds the latest papers. **Once
`Migration:WriteRoutes:PastPapers.Teacher` is `Native` the copy refuses to run** (`NotValid`): teachers then add and edit
papers here, and a copy would put gama-api's older version back over their edits and deletes.

A test server sets `Migration:LegacyDatabase:MaxPastPapers` (the sandbox: 1000) and gets only that many papers by id,
with their files; extra files of the papers left out are skipped. `PastPapersFromId` starts the copy at a paper id, so the
sandbox can hold the newest papers (the ones people see on the live site) rather than the oldest. The copy never deletes,
so moving a test server's window means removing its old copied papers there first. Production leaves both unset and
copies everything.

## Pictures

The paper pages' public pictures are copied from gama-api's server into our **public** buckets (production `v2-files`,
sandbox `sandbox`) with rclone, read-only on the source and checked with `rclone check`, and are served from our CDN:

| Pictures | gama-api folder | Our container (folder) | How a paper reaches it |
|---|---|---|---|
| Paper thumbnails (~37,600) | `uploads/thumbs/` | `Thumbnail` (`thumbnail/`, same relative paths; for any content's thumbnails: tutorials and exams later) | `PastPapers.Thumbnail` without its `uploads/thumbs/` prefix |
| Subject pictures (~230) | `uploads/lessonsPic/` | `SubjectPicture` (`subjectpicture/`) | `LegacyTaxonomyItems.Picture` of the subject |

Owners' avatars are not copied: the owner shown is our own user (`DisplayOwnerUserId`), with our user's avatar, or none.

A subject's picture comes from gama-api's `lessons_pic` (copied by `SyncLegacyTaxonomy`) and is resolved the way gama-api
does: the `.jpg` of the stored name if that file is in the `SubjectPicture` container, else its `.webp`, else none. The
sandbox holds only its own papers' thumbnails. Run the picture copy again before the switch for pictures added since.

## Files

Since 2026-11-25 a paper's files are one list everywhere (the paper page, the directory, the edit form, the admin review,
MCP), each named by its own `id` (`PastPaperFiles.Id`). Before, the API used gama-api's `files: {pdf, word, answer,
extra[]}`, downloads by `fileType` plus `extraId`, and add/edit bodies with `file_pdf`, `file_word`, `file_answer` and
`file_extra`; the frontend had a rule for each. A file in the list:

`{id, role, ext, size, pages, length, type_id, type_title, price}`, in role order:

| `role` | What it is | Rules |
|---|---|---|
| `question` | the question paper | a PDF; required on add; only replaced, never removed |
| `word` | the question paper as Word | doc/docx; one per paper |
| `answer` | the mark scheme | pdf/doc/docx; one per paper |
| `extra` | anything else (insert, audio, ...) | its kind in `type_id` (an extra file type item); any number |

Only stored files are listed (checked size above 0). Ownership stays per role (the purchase's variant `Question`,
`QuestionWord`, `Answer`, `Extra:{CoreExtraFileId}`), so a replaced file stays owned; `CoreExtraFileId` is kept for
that and for gama-api's ids, never shown. The list flags (`q_file`, `a_file`, `q_file_word`) and the search filters
(`pdf`, `word`, `answer`) stay: they say what a paper has, they don't address a file. The directory's `in_file`/`sf_file`
flags and their ids are gone (the list has the files). `PastPaperFileRoles` maps role and kind.

## Native paper page and lists

`NativePastPaperSource` answers the three `PastPapers.Website` calls from the copy, in gama-api's exact output (the
frontend reads it unchanged), so the switch is a setting, not a frontend change:

| Call | gama-api endpoint it replaces | What it returns |
|---|---|---|
| `GetPaperAsync` (`Search/papers/{id}`) | `tests/{id}` | the paper page: its fields, titles of its board/grade/subject/type/variant, files block with prices, owner |
| `SearchPapersAsync` (`Search/papers`) | `tests/search` | `{num, list}`: filtered, sorted, paged; with `directory` and `is_paper=true` the subject directory's items; with `directory` alone the resources directory (the papers of each non-paper type, 50 each); with `directory`, `is_paper=true` and `facet=years` (ours, since 2026-11-18; gama-api ignores it and answers the list) `{num, years: [{edu_year, num}]}`: each year with papers under the filters, newest first, papers without a year or session left out, so the directory page lists the years first and loads a year (`edu_year`) when it is opened |
| `GetPaperLinkAsync` (the exam page) | `tests/{id}` | title and slug of the exam's paper |

The home page's paper and study material counts (`Search/home/stats`, `SearchService.GetHomeStatsAsync`) are the same
list's `num` for the board and grade (`is_paper=1`/`0`, gama-api's `typesstats` counts the same search), so they follow
this route too, cached as before. Its exam and tutorial counts stay on gama-api's `typesstats`.

The **search page** (`Search`, `Search/typesstats`, gama-api's cross-type `search`) follows it the same way, inside the
same cached proxy (`SearchService.SearchAsync`). gama-api's `search?type=test` runs the very paper search of `tests/search`
(same items, order and fields; checked), so once the route is not `Legacy`:

- the Past Papers and Study Materials tabs (`type=test`, with `is_paper`) are the routed paper list's `num` and `list`
  for the search's paper filters, and `types_stats` (unless `noTypesStats`) is gama-api's `typesstats` with `papers` set
  to that total, as gama-api's own search sets it. gama-api's `pageInfo` and filter titles are not sent (the website reads
  neither);
- every other `papers` count (the tab counts from `typesstats`, another type's `types_stats`) is the routed list's total
  for the same filters. Exams, tutorials and the other types stay gama-api's.

With `Legacy` the proxy forwards everything to gama-api exactly as before.

**Related papers** (the "Related Past Papers" row of a paper, exam or tutorial page) come through the same proxy too
(`Search/related`, cached like the rest): its `tests`/`papers` are `GetRelatedPapersAsync(source, id)` on this route (since
2026-11-23 for every page, not only a paper's; the other rows come from their own sources, see
`docs/business/exams-and-content.md`, "Related content"). The native rule is gama-api's `Recommendation_lib::tests` for a
visitor: on a paper page, up to 2 papers this paper's buyers of the last day bought next (same grade and subject, from
`ContentPurchases`, only for a paper refereed B or better); then up to 2 A+ papers of the item's grade and subject (and, on a
paper page, its type), then the same grade and subject within a month of its session (an exam's; a tutorial has none),
newest update first; when a round finds too few, the month and then the subject are dropped, up to 10 papers. Published papers only, never the paper itself.
Two differences, on purpose: gama-api's "trend" picks are left out (they come from a homepage trend file gama-api builds,
not from paper data), and a paper is never listed twice (gama-api's later rounds could repeat one).

Rules it keeps from gama-api (`PastPaperOutput`, tested against live answers):

- Only **published** papers (`Status = Confirmed`, not deleted) are served; anything else is "no result".
- **Filters** of `tests/search`: title, owner (`uid`/`teacher`, gama-api ids until the owner columns are ours), topic
  (with topics linked from other boards, `LegacyTaxonomyRelations`), else subject/grade/board with the papers of their
  linked topics, paper type, referee level, pages, free, pdf/word/answer present, year/month/session, variant, school,
  `is_paper`. **Sort**: default newest year and month first, then the paper number in the type's title, the variant as a
  number, the variant's title, then id; empty values first. 10 per page, at most 50.
- **Text**: the slug is gama-api's `url_title`, sizes are `formatSize` (KB, MB in powers of 1024). Dates are UTC only
  (`subdate`, `up_date`); gama-api's Jalali copies (`subdate_jalali`, `update_jalali`) are not sent, the website does not
  show them. The description is sent as gama-api sends it on Gamatrain: HTML-escaped (`&amp;`, `&lt;`...), line breaks
  included. The website renders it with `v-html`, so it must never go out unescaped. `check_bit` is always `0` (not
  copied; the website does not read it).
- **Topics** are decoded on the page only (list items carry the raw `topic` field). A topic is a season only when its
  title starts with `**`, or by gama-api's metadata test as it behaves (`season` truthy and a metadata value loosely equal
  to `"season"`, so the usual `"season":1` alone is not one).
- **Exams**: the page lists the exams built from the paper with their status (`exams`, the website links the published
  one) in place of `exam_id`. Exams are not moved here: each status is read through `Migration:Routes:Exams`, which is
  gama-api; an exam that cannot be read is left out, as gama-api leaves out one that does not exist.
- **Files block**: a file counts when its checked size is above 0 (see "Checking the copy"); prices are `PastPaperPricing`.
- **Owner**: `DisplayOwnerUserId`, our user (or the fallback user for papers whose owner has no account here); first and
  last name and gender from our user, avatar our user's own or none. The username is never published; `ownerIdentity`
  (shown next to the name) is `@` and our user's own `Handle`, or nothing when they have none.
- **Pictures** are our CDN's (see "Pictures").
- A **view** is counted on the paper page (one `UPDATE`, best effort, so a failed count never fails the page). The page is
  cached by `SearchService`, so this counts once per cache refresh, as the proxy does today. A `Shadow` comparison counts
  nothing (`MigrationRouter.InShadowCall`): gama-api has already counted that view.

The four MCP reads (`PastPapers.Mcp`) are not native yet and answer "not valid"; keep that route `Legacy`.

Expected `Shadow` differences: the owner's name, avatar and `ownerIdentity` (ours), picture links (our CDN), the Jalali
dates (not sent), and view/download counts (the copy's are as of the last `ImportPastPapers`). List totals also differ on
a test server, which holds only part of the papers. Anything else is a bug in the native source.

To switch a server: deploy, run `SyncLegacyTaxonomy` (subject pictures) and `ImportPastPapers`, set
`Migration:Routes:PastPapers.Website` to `Shadow`, read the mismatch log and `GetShadowStatistics`, fix, then `Native`.
Removing the setting switches back.

## Downloads

The paper page downloads through `POST downloads` (`ContentDeliveryService`). Once
`Migration:WriteRoutes:PastPapers.Downloads` is `Native` (a write route: a download charges, so it is never run twice
for a comparison), a past paper file comes from this backend instead of gama-api's `tests/download`, by gama-api's
rules (`PastPaperDownloadService`):

- **Which file**: `fileId`, the file's id in the paper's `files` (since 2026-11-25; before, `pdf`/`word`/`answer`, or
  `extra` with gama-api's extra file id); only a stored file of that paper (checked size above 0). A commission still records
  gama-api's name for the file (`ExternalFileType`/`ExternalExtraId`), and the legacy route asks gama-api by it. Anyone may download a published paper's files; an unpublished paper's only its owner and admins.
- **Price**: what the paper page shows (`PastPaperPricing`, see "Prices"). The paper's owner (`OwnerUserId`) and admins
  download free and count no download, as gama-api's owner and managers. A price of 0 is free.
- **Paid once**: a priced file goes through `IContentPurchaseService` (variant `Question`, `QuestionWord`, `Answer` or
  `Extra:{id}`). A file already in `ContentPurchases` (bought here, or on gama-api and copied, see "Purchases made on
  gama-api") is free again. A new charge is quota first, then points, exactly as before (`ContentType.PastPaper`, its
  price as the quota amount), and the purchase row is written once the link is made.
- **Link**: a signed link to the private bucket's `PastPaper` container, valid a few minutes
  (`FileProvider:PrivateUrlLifetimeMinutes`), saved as gama-api names it (`{id}_{qp|qm|ms|attached}_Gamatrain.com.{ext}`).
  It is made only after the charge; if it fails, the charge is refunded and nothing is recorded.
- **Count and commission**: a download by anyone but the owner or an admin adds one to `DownloadCount`. A charged
  download accrues the owner's commission to `OwnerUserId` (source `Native`); a paper whose owner has no account here
  (`OwnerUserId` null, shown as the fallback user) earns none, as before.

The website fetches the file from the signed link with a script (to show the progress), so the private bucket needs a
CORS rule that allows `GET` and `HEAD` from the website's origins (and the local dev origin on a test bucket); without
it the browser blocks the download although the link works.

`GET downloads/papers/{id}/owned` then reads `ContentPurchases` (all files for the owner and admins) instead of
gama-api's paid flags, and answers `fileIds`, the owned files' ids (extra files too; on the legacy route gama-api's
pdf/word/answer flags are turned into ids). With the route on `Legacy` both endpoints use gama-api exactly as before.

## A teacher's own papers

The teacher's "My papers" page and the paper edit form read through `PastPapers/mine` and `PastPapers/mine/{id}`
(`ITeacherPastPaperService`), answered as gama-api's `GET tests` and `GET tests/{id}?for=edit` answer a teacher. While
`Migration:Routes:PastPapers.Teacher` is `Legacy` they are forwarded to gama-api with the caller's own token; on
`Native` they read the copy (`NativePastPaperSource`):

- **The list**: the papers whose `OwnerUserId` is the caller, in any status, newest first; also those an admin deleted
  (status `Deleted`), not those the teacher deleted. `page`, `perpage` (10 by default, at most 50) and gama-api's exact
  filters (`section`, `base`, `course`, `lesson`, `test_type`, `variant`, `edu_year`, `edu_month`, `id`, `status`, where
  `status=0` means waiting for review). A paper whose owner had no account here when it was copied has no owner and is in
  nobody's list.
- **One paper for the edit form**: the paper page's data in any status for its owner (someone else's unpublished paper
  is denied, `permissionDenied`), with `edit` as gama-api's `editInfo`: `full` while it waits for review or was sent
  back (statuses 0, 2, 3), otherwise `limited` to the description and files; files can be deleted until it is past
  review (not in 1, 2, 4, 6); `reviewNotes` for a paper the review rejected, sent back or deactivated. No view is counted.

- **A file of their own paper** (`GET PastPapers/mine/{id}/files/{fileId}`, since 2026-11-23; by `fileId` since
  2026-11-25), so the edit form can open what the teacher uploaded. A short signed link to the
  private bucket, in any status (deleted by an admin too); someone else's paper is `permissionDenied`. Not a download:
  nothing is charged or counted, and it doesn't follow `WriteRoutes:PastPapers.Downloads`. The same link as the admin review's
  (`PastPaperFileLink`), only checked against the owner. Native only: `Legacy` answers `notSupported`. Before, the edit
  form called gama-api's `tests/download` from the browser, which no route here could move.

gama-api keeps a review's notes in a ticket and the paper's `msg` holds the ticket's id. The copy keeps the ticket's
text instead (tags removed), and the notes are its lines that start with "- " (or the whole text). Admins' access to
other teachers' papers comes with the admin review.

### Uploading, adding, editing and deleting

`POST PastPapers/mine/uploads`, `POST PastPapers/mine`, `PUT PastPapers/mine/{id}` and `DELETE PastPapers/mine/{id}`
take gama-api's paper fields (`POST tests`, `PUT tests/{id}`), except the files: since 2026-11-25 those are one `files`
list of changes (see below), not `file_pdf`/`file_word`/`file_answer`/`file_extra`, and a file is no longer deleted on its
own (`DELETE .../{type}` is gone). While
`Migration:WriteRoutes:PastPapers.Teacher` is `Legacy` they are forwarded to gama-api with the caller's token; on `Native`
this backend does them by gama-api's rules (`NativePastPaperSource.TeacherWrites`):

- **Upload**: a pdf, Word or extra-file kind (gama-api's list), up to 50 MB (gama-api allowed 500 MB; an upload is held in
  memory here, and the largest files, listening audio, are under 40 MB). Stored in the private bucket's `PastPaper` container; the answer's `name` is a key signed for the uploader
  (Data Protection, a day), so nobody can attach a file they didn't upload, such as another paper's. A PDF's pages are
  counted, and `kind=pdf` (the question PDF) also renders its first page as the paper's thumbnail.
- **Add**: teachers (and admins) only, for themselves (`uid` of someone else is `onBehalfNotAllowed`; the admins' "on
  behalf" comes with the admin review); gama-api's required fields by classification and holding level; one paper every
  30 seconds; title and description cleaned as gama-api does (the description then goes through the HTML sanitizer). It
  waits for review (`Pending`) and takes **the next id after the highest one**, so after the last copy it continues above
  gama-api's ids (an add that loses a race tries the next id). New extra files likewise get the next extra file id.
- **Files** (`files` in an add or edit, applied in order): `{role, upload, type_id}` adds a file (for `question`, `word` and
  `answer` it replaces the paper's file of that role), `{id, upload}` replaces a file, `{id, type_id}` changes an extra
  file's type, `{id, remove: true}` removes one. `upload` is the key from the upload; an upload that isn't the caller's,
  has expired or is of the wrong type for the role is ignored, as gama-api ignored a file it couldn't find. An add without
  a question PDF answers `requiredField` `files`. Nothing changes until the add or edit is sent.
- **Edit**: the owner (or an admin). Everything while it waits for review or was sent back; after that only the
  description and files (`ignoredFields` lists the rest). On a **published** paper the owner's edit waits for review apart
  from it and the website keeps the published version (see "Edits to a published paper" below); in the other statuses
  past review (deactivated, edited) the paper goes back to review (`Edited`). A new question PDF or Word file updates
  `LastModifyDate`.
- **Removing a file** (`{id, remove: true}`): the owner until the paper is past review (admins any time); on a published
  paper the owner's removal waits for review with the rest of the edit. The question PDF is only replaced (`lastMainFile`).
- **Delete**: the paper, by the owner until it is past review (admins any time). It is hidden (`IsDeleted`) and keeps its
  stored files, so it can be restored.
- **Storage** (since 2026-11-25): a file that an edit replaces or a delete removes is removed from the private bucket (and
  a replaced thumbnail from the thumbnail container) after the save, unless another row still names the same key (a copied
  path could be shared). A failed removal is only logged. Uploads that are never saved are not removed (see "Checking the
  copy" for the count of unused files).

### Filling the form from the paper

Since 2026-11-25 an uploaded PDF says what it is, so the add and edit forms fill themselves in for the teacher (or admin)
to confirm (`IPastPaperDetectService`). The upload answer's item gets `detected`; nothing is saved by it:

- **What the file is** (any PDF): the first two pages' text (PdfPig) is checked for printed headings: "MARK SCHEME" is the
  answer; "INSERT", "CONFIDENTIAL INSTRUCTIONS", "TRANSCRIPT", "PRE-RELEASE MATERIAL" (capitals for the first and third, as
  Cambridge prints them) are extra files of that type (`fileType`, an extra file type item matched by a word of its title);
  none of these is the question paper (`fileRole`). Solved papers are deliberately not detected: the user picks that
  kind.
- **What paper it is** (the question PDF, `kind=pdf`): a Cambridge cover's component code (`9700/11`: paper 1, variant 1;
  `3248/01`: paper 1, no variant `nv`), session (`May/June 2025`: year 2025, month 6; February/March is 3,
  October/November 11) and level ("AS & A Level", "IGCSE", "(9–1)", "O Level"). The code finds the subject (its title ends
  in "(9700)") under the board's grades, which also gives the grade; "Paper N" is the board's classification item of that
  title its papers use most (a board has several); the variant is the variant item of that title. The title follows the
  site's form: `Biology 9700/11 May June 2025`. `source` is `pattern`.
- **AI fallback**: a question PDF whose text has no such code (other boards, unusual covers) goes to the configured AI
  model (`Ai:Type`) with up to 3,000 characters of the page, asked for JSON only; its answer is mapped the same way
  (subject by code, else by name). `source` is `ai`. Only for the question PDF, never for other files. A PDF without text
  (a scan) or with nothing recognised gets no `detected`; Word files aren't read.

### Edits to a published paper

Since 2026-11-25 the owner's edit of a **published** (`Confirmed`) paper does not take the paper off the website. gama-api
set it to `Edited`, which hid it from search and its page (and from buyers) until a reviewer looked again; a typo fix then
cost the paper its ranking. Now:

- The edit (description, new or replaced question PDF, Word file, answer and extra files, removed files) is kept apart:
  `PastPapers.PendingDescription` and `PastPaperPendingFiles` rows, with `PendingEditDate` set while it waits. The paper
  stays `Confirmed` and everything that serves papers (pages, search, downloads, purchases, the file check) reads only the
  published version. Another edit before the review is merged into the waiting one.
- The answer of `PUT PastPapers/mine/{id}` has `pendingEdit: true` and a message saying so. `GET PastPapers/mine/{id}`
  shows the published version plus `pending_edit`: `waiting`, `date`, `description`, `files` (`id`, `role`, `change`:
  added/replaced/changed/removed, `type_id`, `ext`, `size`, `pages`) and `reviewNotes` of a rejected edit. A change to a
  published file carries that file's `id`; a new file of the edit has a negative `id` (minus its row id), which a later
  edit changes or removes (`files: [{id: -n, remove: true}]`). `GET .../files/{id}?pending=true` opens a file of the edit
  (teacher and admin).
- **Review** (`PUT admin/pastpapers/{id}/review` while an edit waits): `1` approves it, the edit replaces the published
  version (`LastModifyDate` set when the question PDF or Word file changed); `2`/`3` reject it, the edit and its uploads
  are dropped, the published version stays, and the notes show on the owner's form until their next edit. The answer has
  `pendingEdit: approved|rejected` and the status stays `1`. Any other status drops the edit and is set as usual.
- The admin list has `pending_edit` on each paper and the filter `pending_edit=1`; the admin dashboard's paper queue
  counts papers with an edit waiting.
- Admin edits still apply at once.

gama-api's duplicate-file warning (`repeated`, from file checksums) is not reproduced.


## Admin review

The admin panel (`admin/pastpapers`, delegable like the posts) reads every paper from the copy at any time; its changes
are refused (`notNative`) until `Migration:WriteRoutes:PastPapers.Teacher` is `Native`, because until then papers change
on gama-api (and its panel reviews them).

- **List and paper**: every paper that is not deleted (gama-api's admin list), with its owner (`user_`, `owner_name`) and
  filters by owner (`uid`), score and title; a paper opens in any status with full edit rights.
- **Files for the review** (since 2026-11-21): `GET admin/pastpapers/{id}/files/{fileId}` gives a short signed link to the
  question, Word, answer or an extra file of a paper in any status, so the reviewer can read what the teacher sent before
  confirming it. It is not a download: nothing is charged or counted, and it reads the copy whatever
  `WriteRoutes:PastPapers.Downloads` says. Before it, the admin panel had no way to open a paper waiting for review (the
  public page and the download serve confirmed papers, and the download charges anyone who isn't an admin, e.g. a
  delegated reviewer).
- **Review**: the status (waiting, confirmed, rejected, needs changes, deactivated) and notes for the teacher, required
  unless it is confirmed. The notes are saved as gama-api's ticket text is ("- " lines), so the teacher's edit form shows
  them. gama-api's side effects are not reproduced: its notifications and score logs, and deleting a deactivated paper's
  files (they are kept).
- **Score**: the referee score, 0 to 5.
- **Adding for a teacher**: the teacher's fields plus `uid` (the teacher's user id here; it must be a teacher) and
  optionally `price_multiplier`; no 30-second limit. Editing any field (and the multiplier) keeps the status; deleting
  works in any status.

Changes reach the public pages when their cache expires (5 minutes).

## Prices

A paper must cost the same after the move, so gama-api's price rule is reproduced exactly in `PastPaperPricing` (pure,
tested against prices gama-api shows; nothing calls it until downloads move here):

```
main file:  round10(base(ext) * sqrt(pages) * factor(referee score) / 10 * the paper's PriceMultiplier)
extra file: round10(base(ext) * sqrt(length) * factor(referee score) / 10 * its type's price_multiplier)
```

- **Base price per file type** comes from gama-api's `files_price` table (admins edit it there), mirrored with its ids
  into `PastPaperFilePrices` by every `ImportPastPapers` run (added, updated and removed, so the copy always matches).
  Today: pdf 50, doc/docx 100, mp3 30. **A file type with no base price is free** (zip, wav, mp4...).
- **Referee factor** (`RefereeScore`): D (1) 0, C (2) 1, B (3) 1.5, A and A+ (4, 5) 2, none 0. A Word file whose factor
  is 0 gets 0.5 instead.
- **Extra files** use their type's own `price_multiplier` (the lookup item's metadata, copied with the types; 1 when it
  has none) instead of the paper's, and their `Length` instead of pages.
- **Rounding** is PHP's `round(x, -1)`: to the nearest ten, halves away from zero.

## Checking the copy

`IPastPaperFileCheckService.CheckAsync` (Hangfire job `CheckPastPaperFiles`, by hand, never scheduled) lists the private
bucket's `PastPaper` container in full first (a listing that fails part way changes nothing), then looks up every
`PastPaperFiles` row by its `Path`:

- **Found:** its `Size` (bytes) is stored; the paper page shows it.
- **Missing:** `Size` stays null with `CheckDate` set. The file copy missed it or gama-api never had it; the result lists
  up to 20 examples to look into.
- **Unused:** files in the bucket no row points to (left over from uploads never saved, or replaced before 2026-11-25)
  are counted, not deleted. Files of edits waiting for review (`PastPaperPendingFiles`) count as used.

Run it after the file copy finishes, and again after every rerun of the copy. It reads the bucket through
`IFileService.ListFilesAsync` (the configured provider; S3/R2 lists with `ListObjectsV2`).

## Purchases made on gama-api

Today the "already paid" answer for a paper file comes only from gama-api: this backend charges, then calls gama-api's
download, which records the purchase in its `payments` table (see `docs/business/content-delivery.md`). That history
must move with the papers, or every buyer would be charged again after the switch.

`IPastPaperPurchaseImportService.ImportAsync` (Hangfire job `ImportPastPaperPurchases`, by hand, never scheduled)
reads gama-api's `payments` through a column list, so card numbers, IPs and bank fields are never read. It keeps the
paid past paper files only: payment `type` 1 (question PDF), 2 (answer), 8 (question Word) and 12 (extra file, whose
`usage_id` is the extra file's id), with `status` 1, 2 or 3, the same rule as gama-api's own check. Each becomes:

- a `LegacyPastPaperPurchases` row, keyed by gama-api's payment id (a rerun updates it), and
- as soon as its paper is copied and its buyer has an account here (`CoreId`), a `ContentPurchases` row:
  `ContentType = PastPaper`, `ContentId` = the paper id, `Variant` = `Question` / `Answer` / `QuestionWord` /
  `Extra:{extra file id}`, `PaidBy = GamaApi`, `Points = 0` (gama-api took the money). The same file bought twice on
  gama-api is owned once: both copies point at one ownership row.

Ownership is only ever `ContentPurchases`; `LegacyPastPaperPurchases` is gama-api's history and the waiting room for
buyers who have no account here yet (most of them: an account is linked when its owner first signs in through the
gama-api bridge). The daily `LinkPastPaperPurchases` job (`LinkAsync`, reads only this database) moves those over once
the buyer or the paper is here. Run `ImportPastPaperPurchases` again just before the switch: purchases keep being
recorded on gama-api until then.

### Removing the purchase copy

`LegacyPastPaperPurchases` and its service are temporary, for the move only. Once gama-api is shut down and the last
`ImportPastPaperPurchases` has run, decide what happens to the purchases still waiting for a buyer (keep linking them for
a while, or let them go), then remove in one change:

1. the `ImportPastPaperPurchases` and `LinkPastPaperPurchases` jobs (`Startup.cs`), and delete them from Hangfire;
2. `IPastPaperPurchaseImportService`, `PastPaperPurchaseImportService`, `PastPaperPurchaseImportResultDto` and
   `PastPaperPurchaseImportTests`;
3. the `LegacyPastPaperPurchase` entity, with a migration that drops `LegacyPastPaperPurchases`;
4. this section and the matching lines in `docs/database/`, `docs/architecture/cross-cutting-concerns.md` and `CLAUDE.md`.

The ownership rows it made stay: they are ordinary `ContentPurchases` rows (`PaidBy = GamaApi`) and need nothing from the
copy. Nothing else reads the table, so removing it changes no behaviour.
